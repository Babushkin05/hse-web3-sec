# ДЗ №2 — Мастерская игровых предметов (продвинутый вариант)

ERC-1155 игра на OpenZeppelin с обновлением через Transparent Proxy.
Игроки превращают дерево и руду в мечи (`craft`), после обновления до V2
мечи можно разбирать обратно на руду (`salvage`). Вся работа — локально в Foundry.

## Версии зависимостей

| Зависимость | Версия |
|---|---|
| Solidity (solc) | 0.8.28 (пин в `foundry.toml`) |
| forge-std | v1.17.0 |
| openzeppelin-contracts | v5.7.0 |
| openzeppelin-contracts-upgradeable | v5.7.0 |
| openzeppelin-foundry-upgrades | v0.4.2 |

Зависимости подключены как git-сабмодули, коммиты зафиксированы.

## Установка и запуск

```bash
# клонировать с сабмодулями (или после обычного clone: git submodule update --init --recursive)
git clone --recurse-submodules git@github.com:Babushkin05/hse-web3-sec.git
cd hse-web3-sec/hw2

# сборка и тесты (проверочные команды)
forge build
forge test --force
```

Нужен установленный [Foundry](https://getfoundry.sh) (`forge`). В `foundry.toml`
включены `ffi`, `ast`, `build_info` и `extra_output = ["storageLayout"]` — это
требования библиотеки `openzeppelin-foundry-upgrades` для проверки хранилища.

## Правила игры

Предметы ERC-1155:

| id | Предмет | Как получить |
|---|---|---|
| 1 | Дерево | `issue(to, id, amount)` — только владелец игры |
| 2 | Руда | `issue(to, id, amount)` — только владелец игры |
| 3 | Меч | только `craft(n)` |

- `issue(to, id, amount)` — выпуск ресурсов владельцем игры. Разрешены только
  id дерева и руды (меч через `issue` выпустить нельзя), получатель ненулевой,
  `amount > 0`.
- `craft(n)` — при `n > 0` сжигает у вызывающего `3*n` дерева и `2*n` руды,
  выпускает ему `n` мечей и увеличивает глобальный `totalCrafted` на `n`.
  При нехватке любого ресурса операция целиком откатывается.
- `salvage(n)` (V2) — при `n > 0` сжигает у вызывающего `n` мечей, выдаёт ему
  `n` руды и увеличивает глобальный `totalSalvaged` на `n` (счётчик стартует
  с нуля). Разбор не уменьшает `totalCrafted`.
- Обычные переводы ERC-1155 и разрешения операторов работают как обычно и не
  меняют счётчики.
- Обе операции работают только с предметами вызывающего и возвращают результат
  ему же. Списания и счётчик обновляются **до** выпуска токенов и вызова
  получателя (checks-effects-interactions), поэтому отказ получателя
  откатывает операцию целиком.
- События: `Crafted(player, amount)` и `Salvaged(player, amount)`.

## Архитектура и обновление

- `src/CraftingV1.sol` — первая версия (issue + craft).
- `src/CraftingV2.sol` — наследует V1 и добавляет `salvage` + `totalSalvaged`.
- Прокси: OpenZeppelin `TransparentUpgradeableProxy` + автоматически
  развёрнутый `ProxyAdmin`. Деплой V1 и апгрейд выполняются через библиотеку
  `openzeppelin-foundry-upgrades` (`Upgrades.deployTransparentProxy`,
  `Upgrades.upgradeProxy`), все обращения к игре — через прокси.
- `initialize(owner)` вызывается в момент создания прокси. Конструктор
  реализаций вызывает `_disableInitializers()`, поэтому повторная
  инициализация прокси и прямая инициализация обеих реализаций запрещены.
- Владелец игры (`Ownable`) и владелец `ProxyAdmin` — разные адреса;
  обновить прокси может только владелец `ProxyAdmin`.

## Почему данные сохраняются при обновлении

Состояние игры (балансы ERC-1155, разрешения операторов, владелец,
`totalCrafted`) хранится **в хранилище прокси**, а не в контракте-реализации.
При апгрейде меняется только указатель на реализацию (слот EIP-1967), адрес
прокси и все его слоты остаются на месте.

`CraftingV2` наследует `CraftingV1`, поэтому лейаут хранилища V1 сохраняется
без изменений, а единственная новая переменная `totalSalvaged` дописывается
в конец — на нетронутый слот, который стартует с нуля. Совместимость лейаутов
проверяется автоматически библиотекой OpenZeppelin Upgrades при апгрейде
(аннотация `@custom:oz-upgrades-from CraftingV1` на V2, проверка **не
отключалась**): при несовместимости хранилищ `upgradeProxy` отклонил бы
обновление.

## Тесты (`test/Crafting.t.sol`)

- выпуск ресурсов, запреты `issue`: чужой вызов, неизвестный id, меч, нулевой
  получатель, нулевое количество;
- успешный крафт (с событием), нулевое количество, нехватка каждого ресурса
  с полным откатом;
- обычные переводы и разрешения операторов;
- единый сценарий: V1 → выпуск и крафт → разрешение оператору → обновление →
  перевод меча → разбор новым держателем, с проверкой сохранённых данных,
  запрета чужого обновления и повторных инициализаций;
- получатель принимает ресурсы, но отклоняет меч при крафте — все балансы и
  `totalCrafted` не меняются; разбор без мечей отклоняется;
- fuzz-тест `1 <= n <= 1000`: новому игроку выдаётся `3*n` дерева и `2*n`
  руды; после `craft(n)` и `salvage(n)` остаётся только `n` руды, каждый
  счётчик вырастает на `n`.
